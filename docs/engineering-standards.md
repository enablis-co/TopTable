# Engineering standards

## The stack

Vite, React and TypeScript, with Zustand for the store and Vitest for tests. A clone runs on
`npm ci && npm run dev` with nothing else installed.

Node is pinned in [`.nvmrc`](../.nvmrc) and the pipeline reads that same file, so CI cannot
silently run a different version from yours.

Everything is local. No accounts, no server, no sharing, and no ambition to have any. There is no
API layer to build and no auth to plumb, so do not add the seams for one.

## Layout

```
src/
  domain/     The domain model, the rules and the allocation engine. Pure
  store/      The single store, and its persistence
  App.tsx     Placeholder. TT-7 replaces it with the real shell
public/
  scenarios/  The three example weddings, generated by a seeded script
scripts/      Generators and tooling
docs/         This
```

Tests sit next to what they test: `store.ts` and `store.test.ts` in the same folder. A test that
lives in a parallel tree gets forgotten when the module moves.

## The line between the domain and the UI

`src/domain/` is pure. No rendering, no React, no store, and no import of anything that renders. It
takes data and returns data, and it can be reasoned about at a terminal.

This is not tidiness. The allocation engine is the part of this product with real complexity, and
one agent writing both halves produces a solver that knows about React. Two agents own the two
sides — `model-developer` and `ui-developer` — and the boundary is what keeps them from writing
each other's code.

**Adding a rule must not require editing a shared file.** Several people add rules at once, and a
central registry that every one of them has to touch is a queue and a merge conflict.

The UI imports from the domain. The domain imports nothing back.

## TypeScript

`strict`, and four more that earn their keep:

| Setting | Why |
|---|---|
| `noUncheckedIndexedAccess` | This app is arrays of seats. `seats[i]` is genuinely possibly undefined and pretending otherwise is how a seating bug ships |
| `verbatimModuleSyntax` | Type imports are written as `import type`, so what is erased at build time is obvious in the source |
| `noUnusedLocals`, `noUnusedParameters` | Dead code fails the gate rather than accumulating |

`npm run typecheck` covers `src` and `vite.config.ts`. Lint is ESLint with type-aware rules, which
means it needs the same TypeScript project and is slower than you might expect. That is the trade.

## Testing

Vitest, jsdom. Tests describe behaviour in the product's vocabulary — guests, tables, seats, pins,
hard and soft violations — not the shape of the code.

**Tests come from the acceptance criteria, never from the implementation.** A test written against
the code tests what the code does rather than what it was supposed to do; it will confirm a bug as
happily as correct behaviour, and it will pass. The `tester` agent is instructed not to read the
module under test for exactly this reason, and that instruction is the point of it, not a quirk.

Tests are deterministic. No clocks, no randomness, no dependence on run order. The scenario files
are seeded so that regenerating produces identical output, and they are the fixtures: "Small and
cosy" forces every placement at 40 seats for 40 guests, "Adding up" is the realistic middle,
"Celebrity scale" at 200 guests is where things fall over.

## The gate

```bash
npm run typecheck && npm run lint && npm run test
```

Or `npm run verify`, which is the same three.

All of them, not the tests you just wrote. A change is not done because it worked when you tried it
by hand. CI runs the same three on the pull request and again on merge, from the same reusable
workflow, so there is one definition of the gate rather than two that drift.

## Scope

**Never build ahead of the board.** KB-1 lists what is deliberately out of the MVP: drag and drop,
undo, any rule beyond capacity, auto-allocate respecting anything beyond seats and pins, catering
output, export, print, sharing and accounts. All of it is already ticketed under TT-21 to TT-25 and
TT-31 to TT-34.

**A thin ticket is thin on purpose.** Never fill one in, and never invent an acceptance criterion
to have something to build.
